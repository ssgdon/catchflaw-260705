## 2. 판정 규칙 추가안 (v5.8)

기존 분류 규칙 블록 끝에 그대로 붙인다. 소분류 이름은 SUBS와 같은 철자를 쓴다.

```
[판정 규칙 v5.8 — 아래 규칙이 위 설명과 충돌하면 아래를 따른다]
1. 원문(text)으로 판정한다. 번역은 참고만 하고, 번역과 원문이 다르면 원문을 따른다(沒有附水=생수 없음, 甩漏=빠뜨림, 只有地點好=위치만 좋다, unhelpful≠무례).
2. "낡았지만/작지만/오래됐지만 + 깨끗하다·괜찮다·문제없다"는 불만이 아니다. 사실 서술(역에서 10분), 흡연실을 직접 고른 뒤의 담배 냄새, 농담, 의심을 스스로 철회한 말도 불만이 아니다.
3. 원인을 밝히지 않은 결과("잠을 못 잤다", "가려웠다", "알레르기가 났다")로 소분류를 추정하지 않는다. 리뷰가 직접 말한 원인으로만 분류한다.
4. 다음은 어떤 소분류에도 넣지 않는다: 어메니티·비품의 수량 부족·품질·향(수건 개수, 칫솔, 샴푸·비누, 가운, 생수, 냉장고·쓰레기통 없음, 예약 인원만큼 비품 없음), 대욕장·사우나·세탁실 시설 자체(수압·온도·대기 줄), 조식·레스토랑·바·연회·웨딩·비어가든 이용(투숙 안 함), 설계·사용성(샤워기 높이, 열쇠·태블릿 불편), 다른 도시·다른 호텔 이야기.
5. 등장한 물건이 아니라 문제의 성격으로 분류한다: 침대·드라이어·환기팬의 먼지=머리카락·얼룩, 좁은 욕실·샤워실=좁은 방, 배수·변기 물소리=실내 소음, 창으로 들어오는 배기가스·공사 냄새=악취, 흡연 흔적 냄새=담배 냄새.
6. 청결: 머리카락·먼지·얼룩=머리카락·얼룩. 전 투숙객 물건·쓰레기(양말·렌즈·마스크·꽁초), 물때, 청소 누락, 연박 중 수건·휴지 미보충=청소 안 됨. 체크인 때부터 비품이 부족한 것은 4번(판정 없음)이다.
7. 벌레는 벌레·물림을 직접 말할 때만 판정한다. 가려움의 원인으로 더러운 침구를 말했으면 머리카락·얼룩, 원인을 말하지 않았으면 판정 없음, 거미줄은 청소 안 됨이다.
8. 직원: 무례·무시·짜증=불친절. 잘못된 안내·요금·예약 착오·요청 미처리·연락 두절·직원 부재=대응 미흡(직원이 정중했어도 해당). 기다림 자체=대기·지연. 직원 노크·전화로 잠을 깸=실내 소음. 문제를 바로 해결해 줬거나 손님이 스스로 떠났으면 대응 미흡이 아니다.
9. 에어컨: 덥다·춥다·조절 불가=실내 온도. 냄새·꿉꿉한 바람=악취, 눈에 보이는 곰팡이=곰팡이, 먼지=머리카락·얼룩, 소리=실내 소음, 온도 언급 없는 "고장"=낡음·고장. 조명·비데 변좌 난방은 실내 온도가 아니다.
10. 샤워기·수도꼭지·변기 누수, 변기·비데 고장=낡음·고장. 온수·수압은 온수가 안 나오거나 약한 수압, 배수 막힘일 때만이다.
11. TV·리모컨·콘센트=와이파이·TV. 엘리베이터 없음·계단·입구 턱=낡음·고장(역 거리 아님). 철도·도로·지붕 등 건물 밖 소리=바깥 소음.
12. 객실 보안=무단·오입실, 잠금 고장, 사생활 노출, 객실·욕조·대욕장 안 부상(미끄러짐·화상). 단지 낡아서 불안한 시설=낡음·고장, 출입 시간 안내 누락=대응 미흡.
13. 등급 심각: 방 변경·환불·조기 퇴실·숙소 이동·예약 취소로 이어짐, 건강 피해, 안전(부상·무단 입실), 필수 기능 불능(온수 끊김, 냉방 불능으로 잠 못 잠), 별 1–2 리뷰의 강한 분노("최악", "다시는 안 간다").
14. 별 4–5 리뷰이거나 "유일한 단점/그 외엔 만족"이거나 재방문·추천 의사가 있으면 심각이 아니라 주의다. 단, 13번의 안전·건강 피해는 심각을 유지한다.
```

## 3. Few-shot 예시 (24개, 대비쌍 중심)

형식은 `원문 → 정답 / 이유 / v5.7 오답`이다. ★는 v5.7이 이미 맞힌 예시로, 검증 2회에서 지적되지 않은 판정이다. 나머지는 corrections 파일에서 합의된 수정이다.
언어 분포: ko 4 · ja 5 · en 4 · zh-hant 5 · zh 6.

### A. 직원: 태도 vs 처리 vs 대기
**E1 [ko]** "체크인 요청했으나 … 갑자기 아무말도 없이 다른 손님 응대하러감 … 제일 무례한 응대라 정말 최악의 경험"
→ `직원 / 불친절 / 주의`. 이유: 무시·무례라는 태도가 핵심이고 처리 착오가 아니다. v5.7: 직원/대응 미흡.

**E2 [en]** "Extremely unhelpful staff, they will be polite but will never take action / help."
→ `직원 / 대응 미흡 / 주의`. 이유: 정중하지만 조치가 없다는 처리 실패다. 번역 "정말 불친절해요"는 오역이다. v5.7: 직원/불친절.

**E3 [ko]** "더블룸으로 예약했으나, 배정을 이코노미방으로 해줌 … 예약사이트 열고 방 크기 보여주니 그제서야 교체해줌"
→ `직원 / 대응 미흡 / 주의`. 이유: 기다림이 아니라 예약 착오다. v5.7: 직원/대기·지연.

### B. 낡음: 양보절 vs 실제 고장
**E4 [ja]** "建物は古いですが館内は清潔、スタッフの方たちの対応が丁寧で居心地がいい。"(건물은 낡았지만 청결하고 아늑하다, 별 4)
→ **판정 없음**. 이유: 낡음을 양보절로 말한 칭찬이다. v5.7: 객실/낡음·고장/주의.

**E5 [zh]** "房間內的馬桶由我入住當天就出問題了…都只是用毛巾蓋住漏水的地方，然後要我退房後才能修理"(변기가 첫날부터 고장, 새는 곳을 수건으로 덮고 퇴실 후 수리)
→ `객실 / 낡음·고장 / 주의`. 이유: 변기 누수는 설비 고장이고 온수·수압이 아니다. v5.7: 객실/온수·수압.

### C. 좁은 방: "작지만 괜찮다" vs 예약 후회
**E6 [zh-hant]** "房間偏小，但是各項需求都有。"(방은 좀 작지만 필요한 건 다 있다, 별 4)
→ **판정 없음**. 이유: 작지만 괜찮다는 중립 언급이다. v5.7: 객실/좁은 방/주의.

**E7 [en]** "the room was impossibly small. A cabin sized luggage barely fits width-wise … Would rate it 0/5 just because of the size and space."(별 1)
→ `객실 / 좁은 방 / 심각`. 이유: 짐을 펼 곳이 없고 크기 하나로 별 1을 줬으니 예약 후회 수준이다. v5.7: 같은 소분류/주의.

### D. 청결: 머리카락·얼룩 vs 청소 안 됨 vs 비품
**E8 ★[en]** "I found the washroom still have hair on the floor so not clean enough! … however overall is a good hotel"
→ `청결 / 머리카락·얼룩 / 주의`. 이유: 머리카락 실물이 있고 전체 평가는 좋아서 주의다. v5.7: 정답.

**E9 [ko]** "객실은 깨끗하지는 않습니다 ㅎㅎ (누가 끼고 버린 렌즈 있었음..등등)"
→ `청결 / 청소 안 됨 / 주의`. 이유: 전 투숙객 물건이 방치된 청소 누락이다. v5.7: 청결/머리카락·얼룩.

**E10 [zh]** "明明訂了兩人房，毛巾 拖鞋 浴袍 備品 都只有一份"(2인실인데 수건·슬리퍼·가운이 1인분)

## 4. 프롬프트에 넣는 방법

**위치** (일반적인 분류 프롬프트 기준)
1. 역할·목표 → 2. 분류표(SUBS·키워드·기존 경계) → **3. §2 규칙 블록**(분류표 바로 뒤, 출력 형식 앞) → 4. 등급 정의(기존 정의는 두고 규칙 13·14가 덮어씀) → **5. 예시 블록** → 6. 출력 스키마·리뷰 본문.
- 예시는 출력 스키마 바로 앞에 둔다. 모델이 마지막에 본 형식을 따라 하기 때문이다.
- 리뷰 본문이 매번 바뀌므로 규칙과 예시는 고정된 앞부분에 둔다. Gemini 컨텍스트 캐시를 쓰면 접두부가 길어져도 비용이 거의 늘지 않는다.
- **확인 필요**: `analyze_v5.py`가 모델에 원문(text)을 넘기는지, 아니면 번역(tr)만 넘기는지 확인한다. 번역만 넘기면 규칙 1과 E2·E21이 효과가 없다. 원문을 넘기거나 원문과 번역을 함께 넘기도록 고친다.

**예시 형식.** v5.7의 출력 스키마를 정확히 모르므로 아래는 판정 하나 = (cat, sub, grade, quote)를 가정한 형식이다. 필드 이름, 판정 없음 표현(빈 배열 또는 `grade:"정상"`), 리뷰 단위 배열 구조는 **prompt_v5.py의 실제 스키마에 맞춰 바꾼다**. 프롬프트에는 "v5.7 오답" 줄과 ★ 표시를 넣지 않는다. 오답을 넣으면 모델이 그 출력을 따라 할 수 있다.

```
예시(원문 → 출력). 이유는 판단 근거이며 출력하지 않는다.
리뷰: "Extremely unhelpful staff, they will be polite but will never take action / help."
출력: [{"cat":"직원","sub":"대응 미흡","grade":"주의","quote":"they will be polite but will never take action / help"}]
이유: 태도는 정중함. 조치·도움이 없음 = 처리 실패.

리뷰: "建物は古いですが館内は清潔、スタッフの方たちの対応が丁寧で居心地がいい。"
출력: []
이유: 낡았지만 청결하다는 양보절 칭찬 = 불만 아님.

리뷰: "房間空調有非常噁心的霉味，一整個晚上被臭到睡不好"
출력: [{"cat":"냄새","sub":"악취","grade":"심각","quote":"房間空調有非常噁心的霉味，一整個晚上被臭到睡不好"}]
이유: 에어컨 냄새 = 악취. 밤새 못 잠, 별 1.
```
- quote의 언어는 v5.7의 규약을 따른다. 현재 DB의 quote는 한국어 번역이므로 그 규약이면 quote를 한국어로 바꾼다.
- 리뷰 1개에서 판정이 여러 개 나오는 구조라면 E10처럼 같은 리뷰 안에 맞는 판정과 판정 없음이 섞인 예시가 특히 효과적이다. 실제 원문 전체를 넣는 예시를 2–3개 두는 것을 권장한다.

**토큰 예산** (Gemini 기준 대략, 한국어·CJK는 1–1.3자에 1토큰 정도로 계산)
| 블록 | 추정 |
|---|---|
| §2 규칙 14줄 (약 1,650자) | 약 900–1,200 |
| 예시 24개 전체 (리뷰 발췌 + 출력 + 이유 1줄, 오답 줄 제외, 약 3,250자) | 약 1,600–2,050 |
| 24개 전체 합계 | 약 2,500–3,250 (**상한 초과**) |
| **기본 세트 18개** (E3·E5·E8·E11·E15·E22 제외. 규칙 8·10·11과 ★ 정답이 같은 내용) | 약 1,200–1,550 → **합계 약 2,100–2,750** |
- 상한 2,500을 넘으면 다음 순서로 줄인다. 이유 줄을 10자 안팎으로 줄이거나 지움(약 −300) → E4·E6 중 하나 제거(양보절 규칙 2와 겹침). 등급 예시(E7·E17·E23·E24), 체계 밖 예시(E10·E18·E20·E21), 객실 보안 부상 E19는 남긴다.
- 제외한 예시는 eval에서 효과가 부족한 패턴이 보일 때 다시 넣는다.
- 넣은 뒤 `count_tokens`로 실측해 커밋 메시지에 남긴다.
